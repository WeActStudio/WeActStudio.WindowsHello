# 04 · 协议要点与硬件限制的技术依据

这份文档是给"想改驱动 / 想二次开发 / 想确认限制不是驱动 bug"的人看的。
这份文档只记录**已经验证过的结论**和判断依据。更细的逐帧抓包记录
（Windows 官方驱动的 USBPcap 会话、DLL 反汇编笔记）没有随仓库公开，
需要时按 §9 的方法自己复现即可。

---

## 1. 设备

| 项 | 值 |
|---|---|
| VID:PID | `28e9:5159` |
| 名称 | Petaic MOC-5159（GDMicroelectronics） |
| 主控 / 传感器 | GD32W515 / GSL6150 |
| 类型 | match-on-chip（模板与比对都在芯片内，主机拿不到特征数据） |
| 端点 | 2 个 bulk：`0x01` OUT、`0x81` IN（wMaxPacketSize=64）。**没有中断端点** |
| 帧长 | 128 字节定长 |

## 2. 帧格式（bulk OUT，128 字节）

```
[0]      payload 长度
[1]      0
[2]      子命令码
[3..5]   0
[6..]    payload
```

- 校验：前 126 字节累加和放在最后一字节（`moc5159-proto.c` 里实现）。
- **发命令前必须 drain IN 侧残留帧**，否则后续 OUT 全部 NAK 到超时（现象像"设备挂了"）。
- IN URB 长度必须正好 128（回帧是两个 64 字节满包，没有短包收尾）。
- 每会话 `SETUP` 一次（控制 IN `0xC0/0xC0`，1 字节，期望 `0x5C`）。

## 3. 命令表（实测确认的部分）

| 码 | 名称 | 用途 |
|---|---|---|
| `0xC0` | VERIFY_CAPTURE | 验证采集（阻塞，等手指） |
| `0xC1` | VERIFY_MATCHING | 取比对结果（120 字节 payload） |
| `0xC2` | CREATE_ENROLL | 开始登记会话 |
| `0xC3` | COMMIT_ENROLL | 提交登记（携带 80 字节记录） |
| `0xC4` | ENROLL_CAPTURE | 登记采集（阻塞，等手指） |
| `0xC5` | ENROLL_APPLY | 应用本级样本 |
| `0xD5` | DB_SIZE | `[0:4]`=剩余空槽，`[8:12]`=已用条数 |
| `0xD7` | DB_WIPE | 清库 |
| `0xD8` | DB_UPDATE_TPL | 模板自适应写回（匹配成功后做） |
| `0xD9` | DB_DUMP_RECORD_BY_INDEX | 读第 n 条记录（84 字节应答 = 4 头 + 80 记录） |
| `0xDA` | DB_CREATE | 建库（清库后必须做，否则一直 `ev=0x29`） |
| `0xDB` | DB_OPEN | 打开库（按 DB GUID，不存在回 `ev=0x28`） |
| `0xDC` | DB_CLOSE | 关库 |
| `0xDE` | DB_QUERY_BY_SUBJECT | 上层查询接口，**验证流程不调用** |
| `0xDF` | DB_DEL | 删除记录（回显 80 字节记录） |
| `0x13` | 图像块交换 | 2048 字节块，头部偏移 2/3/6/7 必须为 0，从偏移 9 起才是 `0x01` 填充 |
| `0x30` | 会话状态字 | 本机型恒 `0x00`，**不可用于判断手指** |

## 4. 80 字节记录布局（D9 应答 / C3 提交 双证）

```
[0:4]    模板号 tid        新模板 = max_tid + 1
[4:8]    模板数据长度       正常 0x1C (28)
[8:12]   0x00000501
[12:16]  0x05000000
[16:20]  0x00000015
[20:36]  库身份 GUID       全库同值 a1e02ef3-46a8-1266-f2d5-bc0fe9030000
[36:76]  0
[76:80]  全局单调计数器     跨模板递增（Windows 实测 245→249）
```

## 5. 两条链路的真实时序（Windows 官方驱动抓包）

**验证 / 识别**

```
D5 → D9(0..N) ×2 轮 → 0x30 → C0 → 0x13 块 → 0x31 → D5 → C1 → 0x13 块 → D8
```

**登记**

```
… D5 → D9(0..2) → C2
  [C4 → 0x13 块 → 0x31 → C5 → 0x13 块] × 6
  → C3（80 字节记录）→ 0C
```

注意：`C2 / C4 / C5` **全部是 0 字节参数**，只有 `C3` 携带记录本体；
**验证链路里没有任何"选择模板 / 设置主体"的命令**。

## 6. 为什么"多手指只有第一根生效"

证据链（每一条都单独验证过）：

1. **Windows 抓包里也没有多模板**。`verify_truth.pcapng` 的库里 5 条记录是
   `tid=3 ×4`（同一根手指的 4 个样本，cnt 245~248）+ `tid=4 ×1`
   （`[4]=3`，即数据长度为 3，是早期原型写的**无效记录**）。
   也就是说 Windows 在这台设备上从未真正比对过两个不同模板。
2. **删掉第一条就立刻生效**。库里 2 条时，删掉 index0 后剩下的那条马上能匹配
   （用户实测 + `probe ident` 双向确认）。
3. **D9 不能指定比对对象**。只下发 index1 那条记录，用对应的手指按，仍然不匹配；
   D9 payload 发 1 字节还是 Windows 的 16 字节都没有区别。
4. **没有"选模板"命令**。扫过 `0xD0`–`0xE4`：`0xDD` 是未知命令（`ev=0x90`），
   `D3/D2/D4` 任何 payload 都回 `ev=0x26`（本固件不支持），
   `0xDE DB_QUERY_BY_SUBJECT` 在 `PetaicTouchFP.dll` 里**全局只有一个调用点
   `0x180007931`**，位于顶层 IOCTL 分发器（`sub eax, 0x44244C` 系列按 IOCTL 码 switch），
   是给 Windows 生物识别引擎查询用的，验证路径根本不经过它。
5. **C1 之后不能重查**。`D5 + D9(i) + C1` 循环时第二次 C1 无应答 —— 设备已退出比对态，
   所以"一次按压遍历全库"也不可行。
6. **一手指一库不可行**。`0xDB` 换 DB GUID 回 `ev=0x28`（库不存在），
   建第二个库只能靠 `0xDA`，而实际测试 `0xDA` 建第二库会**把设备锁死**（需物理拔插）。

⇒ 结论：**单模板比对是固件行为**，驱动侧无解。驱动只能保证"第一条记录一定是你要用的那根"。

## 7. C1 判定（驱动怎么判断成功/失败）

`0xC1` 应答 120 字节 payload：

```
[0:4]    tick
[4:8]    状态
[8:24]   块1
[24:40]  块2
[108:120] 固定 57 8D 07 08 01 00 00 00 00 00 04 00
```

驱动判据（`moc_c1_matched()`）：

```
命中  : 块1[8] == 块2[8]  且  块1[9:16] 与 块2[9:16] 有差异 (L1 = 16~28)
未命中: 块1[8] != 块2[8]  且  块1[9:16] 与 块2[9:16] 完全相同 (L1 = 0)
```

`ev` 字段与成败无关（正常识别恒为 `0x01`，`0xAF` 只在登记自验证后出现）。
`块1[8]/块2[8]` 曾被误认为"相似度分数"——实际它更像是某个稳定读数，
**真正可判别的是两个块内部的关系**（同一次采集内部比较，不是跨采集比较）。

## 8. 已知未解 / 未做

| 项 | 状态 |
|---|---|
| `C1` 120 字节的完整语义 | 只解出判定用的部分 |
| `0xDE` 的正确 payload 格式 | 未摸到（`ev=0x26`），但验证路径用不上 |
| 登记后 `D9` 回 `ev=0x01`（非 `0x05`） | 已兼容处理，不影响匹配 |
| 多手指 | 固件限制，无解 |
| `C1[7]` 在 `0x49/0x89` 间跳变 | 含义未知（只差 bit7），不影响判定 |

## 9. 想继续挖的话

- 独立诊断工具 `probe` 支持：`info / db / list / dump / ident / mon / cap / ctl / raw / seq / del`
- 会话内连发命令（排查协议时序很有用）：
  ```bash
  sudo ./build/probe seq db:<DBGUID36字节十六进制> d5 d9:00 c1
  ```
- 抓我方驱动流量（不用按压）：`sudo modprobe usbmon && cat /sys/kernel/debug/usb/usbmon/3u`
- 抓 Windows 真实流量：在 Windows 上用 USBPcap 抓，再用 Wireshark 看 bulk 帧。

⚠️ **改协议实验前先备份**：`0xDA` 建库、`0xD7` 清库都是破坏性操作，
一不小心会清掉模板库甚至把 USB 通道搞死（需物理拔插）。
